# Jupiter Prediction API Recon (Phase 0)

**Date:** 2026-08-23 (live-verified with API key against `https://api.jup.ag/prediction/v1`)

## Endpoints used

| Endpoint | Verified behavior |
|---|---|
| `GET /trading-status` | `{"trading_active": true}` — no auth issues with key |
| `GET /events` | Params verified: `category`, `tags`, `filter`, `includeMarkets`. **Envelope is `{"data": [...], "pagination": {start, end, hasNext}}`** — NOT `{"events": [...]}` as doc summary implied |
| `GET /events/{eventId}` | Full event incl. `markets[]`; same `data` unwrap |
| `GET /events/search?query=...` | Works for discovery; same envelope |
| `GET /orderbook/{marketId}` | `yes`/`no` arrays of `[price_cents, qty]` + `yes_dollars`/`no_dollars` decimal-string variants — as documented |

## Up/Down discovery recipe (the important finding)

- Up/down epochs are **NOT** in `filter=live` (that returns sports). Use:
  `GET /events?category=crypto&tags=5m` (or `tags=15m`), `includeMarkets=true`.
- Assets live right now: **BTC, ETH, SOL, XRP, DOGE** on both 5m and 15m. (Spec scope: BTC + SOL; collector records all five, modeling uses BTC/SOL.)
- Upcoming epochs are pre-listed (several future windows visible at once).

## Event/market shape (verified live)

- One event per epoch. Key fields: `eventId`, `subcategory` (asset: `btc`), `tags` (`["crypto","5m"]`), `metadata.slug` = `{asset}-updown-{5m|15m}-{epoch_start_unix}`, `metadata.title` ("Bitcoin Up or Down - August 23, 8:40AM-8:45AM ET").
- Each event has two markets: titles **"Up"** and **"Down"** (marketIds suffixed `-0`/`-1`), provider `polymarket`.
- **Epoch timing:** the market's `openTime` is when *trading opened* (days earlier) — NOT the epoch window. Epoch start = the unix ts embedded in the slug; epoch end = `closeTime` (= start + 300s/900s, verified).
- Event-embedded markets carry **no `pricing` object** — use `/markets/{id}` for pricing fields or `/orderbook/{id}` for live quotes (the collector uses the orderbook).
- `status`: `open|closed|cancelled`; `result`: null until resolved.

## ⚠️ Resolution is TWAP, not endpoint price

Market rules (verbatim meaning): resolves "Up" if the **time-weighted average price (TWAP) of the asset, generated by Chainlink, over the epoch window is ≥ the price at the window start**. Source: Chainlink TWAP data stream (BTC/USD).

**Consequence for Phase 2:** the fair-value model must be an *Asian-style* digital (average of the path vs strike), not the European `Φ(d₂)` endpoint formula in spec §3.2. Mid-epoch, the running TWAP — not just spot — determines distance to resolution. Strike = window-start Chainlink price (not exposed by this API; must be reconstructed from Chainlink/Binance at epoch start and validated against resolutions).

## Fee verification

- No fee data exposed by these public endpoints; `rate=0.07` in `config.yaml` stands on the documented worked examples (100 @ $0.25 → $1.32; 100 @ $0.01 → $0.07 — both match `ceil_cents(0.07·p·(1−p)·n)` exactly). Re-verify at first live order-preview if/when executing for real.

## Rate limits

- None hit during recon at human speed; poll cadence of 2 s across ~10 markets caused no 429s. Collector uses one orderbook call per open market per poll — monitor once running 24/7 and back off if 429s appear.

## Parser changes made from this recon

- Envelope unwrap key: `data` (with pagination).
- `get_events(category=..., tags=...)` replaces `filter=live` discovery.
- New `parse_epoch_event()` → `EpochEvent` (asset from subcategory, horizon from tags, epoch window from slug + closeTime, Up/Down market IDs from market titles).
- Orderbook cents→USD parsing and `best_bid_ask` confirmed against live books (deep ladders, e.g. Up-yes book from 1¢ to 30¢+ with 100–7000 qty levels).
